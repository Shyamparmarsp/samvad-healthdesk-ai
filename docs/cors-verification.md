# CORS verification — measured, not assumed (M4-S16-B)

**Status:** investigated against the running local stack on 2 November 2026. No claim of
"exact-origin CORS works" is made. The measurement below shows the exact-origin allowlist
in `supabase/functions/_shared/cors.ts` **cannot be enforced at the platform layer**, and
records why that is acceptable here.

No service was stopped, restarted or reconfigured. Probes were read-only HTTP requests
sent from inside the `supabase_db_*` container (the only container image with a `curl`
binary; the edge runtime and Kong images have neither `curl` nor `wget`).

---

## 1. What was probed

| Probe | Path | Purpose |
|---|---|---|
| Direct edge-runtime OPTIONS | `http://172.18.0.11:8081/chat-turn` | see what the runtime answers before the function runs |
| Direct edge-runtime POST (no JWT) | `http://172.18.0.11:8081/chat-turn` | see the verifier response headers |
| Kong OPTIONS | `http://kong:8000/functions/v1/chat-turn` | see the gateway's own preflight answer |
| Kong POST (no JWT) | `http://kong:8000/functions/v1/chat-turn` | see gateway headers on a rejection |
| Kong POST (valid anon JWT, allowed origin) | `.../chat-turn` `Origin: http://localhost:5173` | see what the browser actually receives from the function |
| Kong POST (valid anon JWT, **disallowed** origin) | `.../chat-turn` `Origin: http://evil.example` | prove the allowlist is not the control |

The edge runtime has no published host port (`NetworkSettings.Ports` is `{}`), so the
probes were run from a container already on `supabase_network_samvad-backend`.

---

## 2. Measured results

### 2.1 Direct edge runtime, OPTIONS

Allowed origin and a disallowed origin produce an **identical** answer:

```
HTTP/1.1 204 No Content
access-control-allow-origin: *
access-control-allow-headers: authorization, x-client-info, apikey, content-type, x-retry-count, traceparent, tracestate, baggage
access-control-allow-methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
vary: Accept-Encoding
```

The response is generated by the runtime, not by `_shared/cors.ts`: the header list
(`x-retry-count`, `traceparent`, …) is the runtime's own default, and `preflight()` would
have returned `Access-Control-Allow-Origin: <exact origin>` plus `Access-Control-Max-Age`.

### 2.2 Direct edge runtime, POST without a JWT

```
HTTP/1.1 401 Unauthorized
sb-error-code: UNAUTHORIZED_NO_AUTH_HEADER
access-control-expose-headers: sb-error-code
content-type: application/json
```

`verifyJWT: true` is enforced by the runtime **before** the function handler. Note there
is **no `Access-Control-Allow-Origin`** on this response, so a browser cannot read the
401 body — this is why `supabase-js` reports a generic non-2xx for an expired token and
why `src/lib/api.ts` cannot extract a backend error code in that case.

### 2.3 Kong, OPTIONS

```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: *
Access-Control-Allow-Headers: authorization,apikey,content-type
Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE,OPTIONS,TRACE,CONNECT
X-Kong-Response-Latency: 2
Server: kong/2.8.1
```

Answered by Kong's `cors` plugin (the CLI's local `kong.yml` configures
`origins: ["*"]`), not proxied upstream.

### 2.4 Kong, POST with a valid JWT — the decisive result

`Origin: http://localhost:5173` (allowlisted):

```
HTTP/1.1 200 OK
access-control-allow-origin: *
access-control-allow-headers: authorization, x-client-info, apikey, content-type, x-retry-count, traceparent, tracestate, baggage
access-control-allow-methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
access-control-max-age: 600
vary: Accept-Encoding, Origin
Via: kong/2.8.1
```

`Origin: http://evil.example` (NOT allowlisted), same endpoint:

```
HTTP/1.1 404 Not Found
vary: Accept-Encoding, Origin
access-control-allow-origin: *
access-control-allow-headers: authorization, x-client-info, apikey, content-type, x-retry-count, traceparent, tracestate, baggage
access-control-allow-methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
```

Both responses carry `Access-Control-Allow-Origin: *`. The `access-control-max-age: 600`
and `vary: ... Origin` headers are ours (they come from `_shared/cors.ts`), but the origin
value itself is replaced by the platform.

## 3. Which layer injects the wildcard

| Layer | Behaviour | Evidence |
|---|---|---|
| **Edge runtime** (`supabase/edge-runtime`, container `supabase_edge_runtime_*`, `0.0.0.0:8081`) | Answers `OPTIONS` itself and sets `Access-Control-Allow-Origin: *` with its own header/method lists, for every origin. Forces `*` on proxied responses regardless of what the function set. | §2.1, §2.4 (our `max-age`/`Vary` survive, the origin value does not) |
| **Kong** (`kong/2.8.1`, host `:54321`) | Answers preflight with its own `cors` plugin (`origins: ["*"]`) and appends `Access-Control-Allow-Origin: *` to the proxied response. | §2.3, §2.4 (`Via: kong/2.8.1`) |
| **`_shared/cors.ts`** | Computes an exact-origin decision and sets `Access-Control-Allow-Origin: <origin>`, `Max-Age`, `Vary: Origin`. | Headers partially present, origin value never reaches the client |

So there are **two** wildcard layers, and the function-level allowlist is the only one that
is overridden. This is platform behaviour, not a bug in our code, and it is the same
open-source edge runtime used by hosted Supabase.

---

## 4. Production implications

1. **Do not treat CORS as an authorization control.** `ALLOWED_ORIGINS` has no observable
   effect on the hosted platform. The controls that actually protect data are unchanged:
   platform JWT verification (`verifyJWT: true`), `auth.uid()`-derived ownership on every
   read and write, RLS on `reports`/`messages`/`appointments`, and the two narrowly scoped
   `SECURITY DEFINER` RPCs. `AGENTS.md` already states "CORS is not authentication".
2. **A wildcard origin does not widen data access.** Any page can call
   `signInAnonymously()` with the public publishable key and obtain *its own* identity, but
   every query is filtered by that identity. A foreign session or report returns
   `404 not_found`. There is no cookie or ambient credential, so there is nothing to leak
   across identities.
3. **Never add `Access-Control-Allow-Credentials: true`.** It is not set today and must
   stay unset: it is invalid with `*` and would turn a wildcard into a credential-bearing
   policy. Keep bearer tokens only.
4. **A browser at any origin can read a response if it already holds a token for that
   identity.** That is inherent to bearer tokens, not to CORS. It makes token handling
   (no logging, no URL placement, short lived anonymous sessions) the real mitigation.
5. **If a stricter origin policy is ever required**, it has to be enforced where the
   platform does not overwrite it — for example a CDN/reverse proxy in front of the
   functions, or an explicit server-side `Origin` check that rejects the *action* (it still
   cannot hide the response body, because ACAO is `*`). Do not claim the current
   allowlist blocks anything.
6. **401 responses are unreadable cross-origin.** The runtime emits no ACAO on its
   verification failure, so the frontend must treat "non-2xx with no body" as an auth
   failure and re-authenticate; it must not attempt to parse a code.

## 5. What the preflight reports

`scripts/demo-preflight.ts` runs the real OPTIONS probe for `chat-turn` and `speak` and
reports what the browser actually receives:

```
WARNING      CORS OPTIONS chat-turn — platform wildcard ACAO=* (status 200); see docs/cors-verification.md
WARNING      CORS OPTIONS speak — platform wildcard ACAO=* (status 200); see docs/cors-verification.md
```

`WARNING`, never `PASS`: the allowlist is not in force. It stays a warning rather than a
failure because the platform behaviour is expected and the security model does not depend
on it. If a future platform release honours the function headers, the same probe flips to
`PASS — exact origin`, with no code change.

## 6. Reproducing

```bash
# container IP of the edge runtime
docker inspect supabase_edge_runtime_$(basename "$PWD") \
  --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'

# probes (read-only; the db image is the only one with curl)
docker exec supabase_db_$(basename "$PWD") sh -c '
  curl -s -i -X OPTIONS http://<runtime-ip>:8081/chat-turn \
    -H "Origin: http://localhost:5173" -H "Access-Control-Request-Method: POST"
  curl -s -i -X OPTIONS http://kong:8000/functions/v1/chat-turn \
    -H "Origin: http://localhost:5173" -H "Access-Control-Request-Method: POST"
'

# and the automated form
deno run --allow-net --allow-env --allow-read --allow-run scripts/demo-preflight.ts
```

The runtime port is `8081` locally (from `/proc/net/tcp`, `1F91`). It is not published to
the host, which is why the probe runs inside a container on the same network.
